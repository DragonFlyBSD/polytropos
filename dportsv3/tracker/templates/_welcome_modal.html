First Turnsv1

How the tracker turns a failed build into a fix you can ship.

    Chapter 1 · Orientation

    Where failures land

    Nobody files a ticket here. Every port that fails a dsynth build uploads its own evidence, and the tracker keeps three things apart. Most early confusion is these three run together.

    Issue
    One fingerprinted problem — the thing you resolve. devel/py-cffi · @2026Q3 · fp 9f21e0c4bb31d70a
    Occurrence
    One build failure of that problem, with its logs, its port files, and whatever the agent did about it. The API and the queue call it a bundle.
    Job
    One piece of runner work against an occurrence: triage, patch, verify, confirm build. Jobs come and go; the occurrence keeps their result.

    Coming from Sentry, the first two words mean what you expect. The difference is what happens between them: an agent reads the failure and tries to fix it before you ever look, so an issue usually arrives with an answer attached — and your job is to judge it.

    Chapter 2 · Grouping

    How a failure becomes an issue

    Grouping is not by port. The same port fails for unrelated reasons, so failures are grouped by the first line of logs/errors.txt, canonicalised until only the reason is left.

    noteThe origin is part of the key, so the same compiler error in two ports is two issues — each port needs its own fix. A failure with no usable error line still gets an issue: all of them for one target and port collapse into a single catch-all instead of one per build.

    Chapter 3 · The loop

    Who does what

    The runner goes as far as it can without you. Your side starts when a fix exists and someone has to judge it, and ends two clicks later.

    noteWhile a job holds an occurrence it is deliberately kept out of the worklist. If work is in flight there is nothing for you to decide yet, and a queue that shows it anyway trains you to ignore it.

    Chapter 4 · The queue

    Your worklist

    The landing page is not a list of failures. It is a list of decisions, banded by which decision each one is waiting for, in the order worth doing them. Every row opens the same workspace; the band is what says which decision is waiting.

    Inside a band, the issues seen most often float to the top, then the most recent. Three sightings or more earns a systemic tag: one port failing six times and six ports failing once are different problems, and the tag is what tells them apart at a glance.

    Chapter 5 · State

    The issue lifecycle

    Four states are stored. regressed is not one of them — it is recomputed every time a page renders, so the badge can never disagree with what the builds actually did.

    Two details worth knowing

    • Two greens, not one. A single green confirm build is provisional — networks and toolchains flake, and one lucky build would close an issue that is not fixed. The threshold is runner.confirm_green_threshold, default 2. Three builds that cannot run at all (env gone, nothing to replay) stop the retries and hand it back to you, spaced by a backoff that starts at a minute and doubles to an hour.
    • Green Head is a watermark, not a build. When a confirm build resolves an issue, the tracker records which farm build was current at that moment. A later build re-emitting the same fingerprint is past that mark, and that is what regressed means — build ordinals, no clocks, no skew. An issue you resolved by hand has no watermark and falls back to comparing timestamps.

    Chapter 6 · Actions

    What each action needs

    Buttons appear when the state allows them, and the server checks the same rule again — a stale page cannot talk you into an illegal move. Here is every status an occurrence can show you.

    The rules behind the buttons

    • Accept needs a verified rebuild. The button renders on the agent-fixed lane so you can see where the path leads, but stays disabled until something has actually built the change.
    • Verify is blocked only by Accept and Reject. Even a discarded occurrence can be verified — sometimes you want to know whether the fix you threw away worked.
    • Take over claims the port. Auto-triage stops for it until you Release, so the agent will not queue work against a file you are editing.
    • Reopen is the only thing a closed occurrence accepts; it clears the disposition and puts the problem back in front of you.
    • Build now and Cancel build exist only while an issue is resolving — they nudge the confirm build the runner is already going to schedule.
    • A merged pull request beats everything. The tree already changed, so upstream wins over whatever the local disposition said. The tracker notices on its own, at most once every five minutes per open PR.

    Reference

    Glossary

    The words this tracker uses in a sense of its own.

    origin
    A port's path in the tree, devel/py-cffi. Half of an issue's identity.
    target
    The ports branch being built, @2026Q3. The other half.
    occurrence · bundle
    One failure and its evidence. The UI says occurrence; the API, the queue and the disk say bundle.
    fingerprint
    16 hex characters of the canonicalised first error line.
    dsynth
    The bulk builder. Every failure here started as one of its build logs.
    dev-env
    The DragonFly chroot the agent edits and rebuilds in. Your checkout is never touched.
    dops
    The overlay language a port's DragonFly changes are written in. What the agent edits.
    confirm build
    An unattended rebuild that exists to prove an accepted fix, not to produce packages.
    Green Head
    The farm build that was current when a confirm build proved a fix — the line a regression has to cross.
    systemic
    Seen three times or more. Usually one cause behind many failures.
    delivery
    What Accept does with the fix: a pull request, or a patch file when no forge is configured.
    manual queue
    Escalations waiting for you to add context and send them back to the agent.
